# Монтаж по битам

Метод: как получить монтаж, который «попадает в ритм», а не «идёт рядом с музыкой».
Реализация: `scripts/beat_grid.py`, проверка — `tests/test_beat_grid.py`.

## Когда включать

- **BGM уже выбран** → сначала строим сетку, потом режем сцены: каждая склейка и
  каждый ударный кадр (impact, slam, переброс) попадают в узел сетки.
- **BGM ещё не выбран** → не строим сетку. Сначала выбирается музыка под смысл,
  потом ритм; обратный порядок даёт ролик, подогнанный под случайный трек.

**Железное правило: музыка первична.** Пока сетка не проверена, не проектируем
раскадровку. Если длительность не сходится — правятся временные параметры сцен,
а не текст.

## Порядок

```bash
# 1. Сетка по выбранному BGM (fps = fps вашего рендера)
~/.venvs/shotcraft/bin/python scripts/beat_grid.py bgm.mp3 --fps 30 --json grid.json

# 2. Смотрим вердикт: OK/WARN по остатку, по полу/двойной сетке, покрытие ударов
# 3. Кадры берём ТОЛЬКО из grid.json → frames, не пересчитываем вручную
```

## Метод: почему именно так

### 1. Скалярный BPM врёт — сетку строим по последовательности битов

`librosa.beat.beat_track` возвращает и скалярный tempo, и список времён битов.
Скаляр ошибается на проценты (в первоисточнике-апстриме: 129.2 против реальных
131.97), поэтому строим **равномерную сетку** `t_i = phase + i·T` по всему списку.

### 2. Период — методом PDM, а не прямой МНК по всему списку

Бит-трекер иногда **теряет** удар, **удваивает** его или дописывает лишний на
затухании в конце трека. Прямой МНК по всему списку ловит выбросы и уводит
и BPM, и фазу.

Поэтому период ищется перебором: для каждого T около медианного интервала
считается, насколько плотно фазы `beat mod T` собираются в узкий пик. Выбросы
дают ровный фон и на пик не влияют. Победитель — T с самым узким пиком.

### 3. Фазу берём по энергии сигнала, а не из вывода бит-трекера

Здесь была самая дорогая ошибка, и она неочевидна. Медиана сдвигов битов
(«фаза как у трекера») даёт монтаж **систематически на ~20 мс позже** удара —
на слух это «почти в такт», то есть ровно тот дефект, из-за которого весь метод
и затевается. Измерено на клик-треках с известной истиной (`t = k·T`):

| Способ | Смещение от реального удара |
|---|---|
| `beat_track`, hop 512 | 34 мс |
| `beat_track`, hop 256 | 22 мс |
| `beat_track`, hop 128 | 16 мс |
| `beat_track`, hop 64 | 16 мс |
| пик `onset_strength`, hop 256 | 12.8 мс |
| пик `onset_strength`, hop 64 | 5.2 мс |
| **скан по максимуму энергии (метод)** | **≤ 3 мс** |

Важное: лаг `beat_track` **не исчезает** при уменьшении hop — это не квантование
кадрами, а лаг алгоритма. У пика `onset_strength` смещение пропорционально hop —
артефакт оконного спектрального потока. МНК по временам битов эту систематику
воспроизводит, а не убирает, поэтому у трекера он берётся **только для периода**,
а фаза ищется несмещённо: огибающая энергии → локальный максимум в окне ~8 мс →
перебор фазы с шагом 1 мс → максимум суммы энергии в узлах сетки. Шаг 1 мс —
это 1/30 кадра при 30 fps, то есть ошибка заведомо ниже одного кадра.

### 4. Две метрики, которые нельзя путать

В выводе инструмента есть два похожих числа, и путать их — верный способ
обмануть себя:

| Метрика | Что измеряет | Для чего годится |
|---|---|---|
| `residual_ms` | разброс битов **трекера** вокруг прямой | ровность темпа на длине трека (то, что требует апстрим на 2 минутах) |
| `grid_error_ms` | расстояние реальных ударов до узлов **сетки** | встанет ли склейка в такт — настоящий показатель качества |

`residual_ms` у beat_track всегда «грязный» из-за его собственного лага: 6–20 мс
при идеальной сетке. Судить по нему о попадании в удар нельзя.

### 5. Индекс бита — арифметика, а не позиция в массиве

`i = round((t - phase) / T)`. Как только трекер потерял один удар, «номер = позиция
в массиве» ломается и вся вторая половина трека уезжает на бит. Индекс,
вычисленный из времени, устойчив к пропускам.

### 5. Два прохода отсева — не оптимизация, а необходимость

Первый проход по всему списку с грубым порогом (15% периода), фит по инлайнерам,
затем второй проход с точным порогом (6%) и финальный фит. **Один** одиночный
выброс без второго прохода раздувает остаток по всей длине: в тестовом прогоне
концевой «фантомный» бит дал 60 мс остатка на двухминутном треке вместо 10 мс.

### 6. В кадры переводим один раз, в самом конце

Раннее округление копит ошибку: при шаге 13.846 кадра округление каждого шага до
13 (или 14) даёт дрейф **38 кадров** к концу двухминутного трека — это больше
секунды. Инструмент печатает эту цифру прямо в выводе, чтобы её не забыли.

### 7. Склейка — жёсткая, затухание перед ней убивает ритм

Соблазн поставить fade на 4 кадра перед склейкой ломает всё, ради чего строилась
сетка. Первый шаг затухания при такой длине даёт перепад **25%** — это визуально
более сильное событие, чем сама склейка, и глаз читает ритм по нему: замеры
готового ролика показывали пики движения на **3 кадра раньше** бита (100 мс).
Ритм задаётся входом шота — движением камеры или сменой кадра, а не затемнением.
Если затухание нужно по драматургии, оно не должно начинаться на бите.

### 8. Проверяем не только сетку, но и готовый ролик

Сетка может быть идеальной, а монтаж — разъехаться (шот привязан не к тому биту,
затухание съело удар, расписание посчитано со сдвигом). Поэтому последний шаг —
проверка по файлу: склейки ищутся как выбросы в покадровом различии и сверяются
с `frames` из сетки. Расхождение меньше кадра = монтаж стоит по битам.

```bash
# демонстрационная сборка целиком: аудио → сетка → рендер → проверка склейек
cd demo
~/.venvs/shotcraft/bin/python ../scripts/beat_grid.py audio/bgm.wav --fps 30 --json out/grid.json
npx remotion render comp/index.tsx ShotcraftDemo out/demo.mp4
~/.venvs/shotcraft/bin/python check_cuts.py out/demo.mp4
```

## Чтение вывода

| Строка | Что значит |
|---|---|
| `OK сетка равномерная… ±X мс` | машина играла под метроном, одна BPM на всю длину |
| `WARN остаток… смена темпа` | темп плавает (живая запись) — резать сетку на сегменты |
| `INFO отсеяно N бит(ов)` | трекер потерял/удвоил удары — они не в сетке |
| `WARN лучший вариант — half_0.5x / double_2x` | кандидат на полу/двойной темп: проверять по слуху |
| `INFO покрытие сильных` | сколько киков/снейров лежит на сетке (±полкадра) |

Порог остатка зависит от длины: 15 мс — это ~150 ppm. На 30-секундном фрагменте
такой допуск мягкий, на 2-минутном — требует вдвое большей точности. Поэтому
для коротких окон порог масштабируется по числу битов.

## Полу/двойная сетка (half/double)

Классическая ловушка: 70 BPM легко читается как 140. Критерий — не слух, а
**сила удара под гребёнкой**: считается средняя энергия onset-огибающей в узлах
сетки, делится на среднюю по треку. У правильной сетки коэффициент заметно выше.
Переключение на половинную/двойную предлагается только при выигрыше больше 10%,
иначе остаётся базовая: полу/двойная сетка — подмножество/надмножество той же
сетки, и «не хуже» она почти всегда формально.

## Проверка метода

```bash
~/.venvs/shotcraft/bin/python tests/test_beat_grid.py
```

Синтетический клик-трек с известным BPM и фазой. Проверяются: попадание в темп,
фаза внутри первого бита, постоянный шаг, что сетка лежит на прямой, отсев
выбросов и — отдельно — что на 120 секундах остаток укладывается в 15 мс.

## Границы применимости

- Трек короче 10 секунд или с малым числом ударов — инструмент откажется; это
  честнее, чем выдать сетку по 4 битам.
- Живая запись с плавающим темпом требует сегментной сетки: разбейте трек по
  сменам темпа (по слуху или по резкому росту остатка) и прогоните каждую часть.
- Инструмент даёт сетку и кадры, но **не решает, что ставить на бит**. Это
  режиссёрская работа: склейка, impact или старт движения — на выбор автора.
